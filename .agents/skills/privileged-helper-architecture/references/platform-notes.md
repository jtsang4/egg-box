# Platform notes

What had to be learned for the two desktop platforms. The statements about real Windows and macOS service behaviour were not exercised end to end on this developer's machine (`host-safe-verification`): they come from the design, the OS documentation and unit tests of the pure parts, so verify them on a disposable machine before relying on them.

## Windows

- **Service**: LocalSystem, automatic start, restarted by the system when it fails (recovery actions). Registration needs administrator rights, and the registration step refuses a program an ordinary user could replace, because the service would run it as SYSTEM.
- **Handler**: accepts stop and shutdown, session-change notifications (`SERVICE_CONTROL_SESSIONCHANGE`) and power notifications (`PBT_*`), and turns them into agent events. Stopping has a budget (the system ends a service that takes too long): disconnect and clean up inside it, and report exit codes to the service manager.
- **Start-up failure**: a service has no console. Write the reason to a file an administrator can read and return the exit code.
- **Sessions**: a tracker follows whether the authorized user is signed in. Sign-out, or another person taking the screen, ends the user's presence and the connection is taken down; locking the screen is not such a notification, so a locked machine stays connected. If the service starts while the user is already signed in, seed the tracker with that session.
- **TUN driver**: the Wintun adapter is carried inside the TUN library, so there is one DLL version to track and its license (prebuilt-binaries terms) is separate from the library's: name it in the third-party notices (`go-release-quality-gates`).
- **Adapter cleanup**: remove a leftover adapter only if its description says it is the tunnel driver's; wait until it is really gone; if not, tell the person where to remove it by hand (Network Connections).
- **Pipe security**: explicit SDDL and peer facts (`authorization-and-ipc.md`).
- **Elevation**: the app asks for administrator rights once (the "runas" verb) to install and start the service; afterwards it needs none.
- **Pure rules in files without a `_windows` suffix** (SID syntax, SDDL building, peer policy, path containment, session tracker, owner record) so they run in every CI job and on a Mac.

## macOS

- **Service registration**: a LaunchDaemon described by a plist inside the app bundle (`Contents/Library/LaunchDaemons/<label>.plist`, with the program given by a bundle-relative `BundleProgram` and the Mach service name under `MachServices`), registered through `SMAppService` (macOS 13 and later). The first registration waits for the person to switch it on in System Settings (Login Items). The app only reports where that stands (0 not registered, 1 enabled, 2 waiting for approval, 3 not in this build) and opens System Settings; it cannot toggle boot start itself. **Never call `register()` during verification on a development machine.**
- **Swift bridge**: what only Swift or Objective-C blocks can do (XPC, SMAppService, SCDynamicStore callbacks, sleep and console-user notifications) sits in a small dynamic library of plain C functions (`@_cdecl`). Strings pass as C strings; failures return a negative number plus a message written into a buffer the caller provides, so there is no hidden "last error" and calls are thread-safe; no Swift or Objective-C object crosses into Go. The Go side loads it with a pure-Go dynamic loader (purego): with cgo off, its callback support handles calls arriving on foreign threads. Run asynchronous work on one private queue.
- **XPC**: introduction plus fd hand-over, requirement strings, anonymous listener for tests (`authorization-and-ipc.md`).
- **DNS**: while the tunnel is up, the system resolver must ask the tunnel. Without editing the person's network settings, add a temporary resolver "service" in the dynamic store (what `scutil` edits): one that has only DNS and matches every domain. It is state, not configuration: it does not survive a restart and nothing changes in System Settings. It carries a token only the service knows so that removal can tell its own entry from somebody else's under the same key. Writing it needs root; keep the store behind an interface and test against a fake.
- **Watchers**: the console user (the login window means nobody) and sleep/wake. After a wake the uplink is probably different, which feeds the debouncer.
- **Signing**: ad hoc signing is enough to build and inspect; distribution needs a Developer ID and notarization. Sign inside-out (the dylib, then the service under its own identifier, then the bundle). The requirement strings are derived from the team the running program was signed by, so an ad hoc build trusts only itself.
- **Packaging**: the package is non-relocatable and root-owned, so the install-location rule (every parent root-owned, not world-writable, group-writable only by `admin`) holds. The pre-install script stops a running service through launchd and leaves the upgrade marker; the post-install script starts it (`lifecycle-and-installers.md`).
- **The plist's keys that matter**: `MachServices` starts the service on demand when the app connects; `RunAtLoad` starts it with the computer once allowed; `KeepAlive` with `SuccessfulExit=false` restarts it after a crash but leaves it stopped after a clean exit (which is what asking it to stop is), and the next start cleans up what the crash left; `ThrottleInterval` stops a service that cannot start from being restarted in a loop; `ExitTimeOut` must be longer than the service's own shutdown budget so launchd never cuts it off while it is putting the network back; `ProcessType=Interactive` keeps the system from slowing a program that carries the computer's traffic; `StandardOutPath` and `StandardErrorPath` point at a log file, because launchd otherwise discards the output; `AssociatedBundleIdentifiers` ties the daemon to the app in System Settings.
- **launchd**: the working directory is `/` and the environment is root's.
