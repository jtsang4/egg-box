# 分流与节点选择设计

本文是 EggBox 分流（原"规则"）和节点选择的完整设计，用来替换现有的三个路由预设、自定义规则列表和单一的节点选择。实现时以本文为准，`docs/design.md` 里的进程架构和安全边界保持不变。

## 1. 为什么要改

现有设计的问题，都是从用户实际使用时发现的：

- **只能选"代理 / 直连 / 拦截"。** 最常见的需求，比如"AI 走美国、Netflix 走新加坡、其余走香港"，现在做不到。
- **用不了社区规则集。** 现在只认 SagerNet 的 4 个固定规则集，没有地方填链接。教程、朋友、机场给的规则（blackmatrix7、Loyalsoldier、ACL4SSR、anti-AD 等）都导不进来，只能一条条手写。
- **订阅自带的分流方案被丢掉。** 很多机场的订阅（sing-box 或 Clash 格式）带有完整的分组和规则，现在导入时只留下节点。
- **规则一次只能加一条。** 不能批量粘贴，不能单条停用，也看不到预设实际展开成了哪些规则。
- **固定的节点会悄悄失效。** 节点身份是整份节点配置的哈希，服务商轮换密码或 IP 后哈希就变了。这时选择会静默回到"自动"，用户不知道。
- **重名节点分不清。** 多个订阅里有同名节点时，除了节点页，其他地方都看不出它来自哪个订阅。

## 2. 目标与原则

1. **小白零配置。** 导入订阅、点连接，就有合理的分流：国内直连、国外代理，常见服务各归其类。
2. **社区规则直接可用。** 热门项目的规则集，不管是 sing-box、Clash、Surge 还是 AdGuard 格式，都能直接添加，用户不需要知道格式差别。
3. **从用户的问题出发。** "这个网站走错了"应该能直接改，而不是让用户去想"该写一条什么规则"。
4. **选择不会悄悄丢失。** 订阅刷新、节点改名、换方案时，尽量保住用户的选择。真的保不住时，明确告诉用户。
5. **安全边界不变。** agent 仍然不主动联网，只接受 GUI 交来的资源；订阅内容仍然按凭据对待。

非目标：需要解密 HTTPS 的规则（URL-REGEX、USER-AGENT）、脚本和重写、负载均衡。

## 3. 概念

| 名称 | 含义 |
|---|---|
| 节点 | 订阅里的一个代理服务器。所有已启用订阅的节点合在一起使用，可以叠加。 |
| 主出口 | 默认的出去方式：自动（最快）、某地区自动，或指定节点。托盘和首页显示的就是它。 |
| 分流方案 | 一张有序清单：我的例外 → 分流项 → 兜底。**同一时间只有一个方案生效。** |
| 分流项 | 一类流量，例如"AI 服务"。由名字、图标、一个或多个规则来源、一个走向组成，可以单独开关。 |
| 规则来源 | 分流项背后的规则数据：一个规则集文件（任意受支持的格式），或几条手写条目。 |
| 走向 | 某类流量的去处：跟随主出口、某地区自动、指定节点、直连、拦截。 |
| 我的例外 | 用户自己的规则，独立于方案，永远排在最前面，切换方案也不会丢。 |
| 兜底 | 没有命中任何规则的流量，它的走向。 |
| 规则目录 | 应用内置的可搜索目录，收录热门规则集项目里的常见分类。 |

用户界面里不出现"规则集""策略组""srs""behavior"这些词。用户只会看到"分流项""来源""走向"。

## 4. 用户体验

### 4.1 首次使用

1. 用户导入第一个订阅。
2. 如果这个订阅附带分流方案，就直接采用它，并提示一次："已使用「机场A」附带的分流方案，可以在分流页切换。"
3. 如果没有附带方案，就使用内置推荐方案（第 9 节）。
4. 用户点连接，就能正常用。之后再导入的订阅不会自动切换方案（见 4.7）。

### 4.2 分流页

导航里的"规则"改名为"分流"。页面从上到下依次是：

1. **标题栏。** 标题"分流"，副标题是"方案：内置推荐 · 13 个分流项"。右侧有两个按钮：「测试网址」和「添加分流项」。
2. **方案栏。** 显示"当前方案 [内置推荐 ▾]"，旁边是来源说明，例如"跟随「机场A」更新 · 2 小时前"。菜单里有：另存为我的方案、恢复默认、删除（仅限"我的方案"）。
3. **我的例外。** 默认折叠，标题上显示条数。没有例外时显示一行提示："网站走错了？在连接列表里右键，或者在这里粘贴域名。"
4. **分流项列表。** 按生效顺序排列，每行包括：
   - 图标和名字；
   - 来源摘要，例如"MetaCubeX · 2 个来源 · 今天更新"；
   - 状态，只在有问题时显示：「3 天未更新」「暂不可用」「部分规则不支持」；
   - 走向，是一个下拉选择，见 4.8；
   - 开关；
   - 行菜单：详情、上移 / 下移（规则见 4.7）、删除（规则见 4.7）、复制到我的方案。
5. **兜底。** 固定在最后一行，显示为"其他所有流量 → [跟随主出口 ▾]"。

点击某个分流项，打开它的**详情**，内容包括：

- 每个来源的名称、所属项目、格式、条数（域名 x、IP 段 y）、不支持的条数及类型、最近更新时间、原始链接；
- 「添加来源」：把其他规则集合并进这个分流项，也可以添加手写条目；手写条目可以直接在详情里编辑；
- 「移除来源」。

### 4.3 添加分流项

「添加分流项」对话框有三个入口，选好之后进入同一个确认步骤。

**A. 搜索目录（默认入口）。** 输入"Netflix""AI""广告"这类关键词，结果按三类依次排列：

1. 目录里精选的条目，带中文名、简介、推荐来源，以及可选的其他来源；
2. MetaCubeX 的全部 geosite 名称（约 4000 个），显示为"geosite: xxx"；
3. 其他项目的分类，比如 blackmatrix7 的约 670 个分类。

**B. 粘贴链接。** 支持 GitHub 页面地址（自动换成原始文件地址），也支持带镜像前缀的地址（自动识别出真实来源）。客户端下载后自动识别格式，并给出预览：

> 识别为 Clash 规则（classical），共 1,234 条：域名 1,100 · IP 段 130 · 其他 4。其中 4 条是 sing-box 不支持的类型（USER-AGENT），已跳过。

如果粘贴的其实是订阅链接，提示"这看起来是一个订阅，要添加到订阅吗？"；如果下载失败，提示可以换镜像重试。

**C. 从其他方案添加。** 列出其他可用方案（内置推荐、各订阅附带的方案、我的方案）里的分流项，可以把单个分流项复制到当前方案。

**D. 手写条目。** 用户自己写一组规则，作为一个独立的分流项，比如"公司内网"的 10 个域名走直连。输入方式和"我的例外"的文本编辑相同（4.4）：可以每行一条，可以用 Clash 写法，也可以逐条选类型添加；只是手写条目不写去向。和例外的区别是：

- 一组手写条目共用同一个走向；
- 可以排在分流项中间的任何位置；
- 会随方案切换，不像例外那样全局生效。

已有分流项的详情里，「添加来源」也可以选"手写条目"，给现成的分流项补几条规则。比如给"AI 服务"补一个规则集里漏掉的域名。

**确认步骤**需要用户填三项：

- 名字：从目录条目或文件名预先填好，手写条目则由用户填写；
- 走向：按目录建议预选，比如广告类是"拦截"，国内类是"直连"，其余"跟随主出口"；
- 位置：默认按目录给的优先级插入（拦截类最前，具体服务排在公司大类之前，国内 / 国外大类排在最后），也可以选"放在 X 之前"。

### 4.4 我的例外

- **适用范围。** 例外是全局的，不属于任何方案，永远最先匹配。
- **排序。** 按列表顺序匹配，用户可以排序。
- **单条添加。** 可以选类型：域名、域名后缀、关键字、正则、IP 段、端口、进程名、进程路径。
- **文本编辑。** 全部例外以文本打开，每行一条，行的顺序就是匹配顺序；改完整体保存，粘贴一批规则也在这里完成。写法是 Clash 的 `类型,内容,去向`，也可以只写域名、IP 段或程序名，由应用识别类型：`example.com` 识别为后缀，`1.2.3.0/24` 识别为 IP 段，`*.exe` 或程序名识别为进程。含逗号的字段用双引号括起来（内部的双引号写两次）。
  - 去向：`DIRECT` 是直连，`REJECT` 是拦截，`REGION:JP` 是某地区最快的节点，`NODE:节点名` 是某个节点；不写去向就跟随主出口。与某个分流项同名的去向，取该分流项此刻的走向（之后不跟着变）。
  - 行首加 `#` 表示停用这条例外；不是完整规则的 `#` 行是注释，不会保存。
  - 同名节点：几个订阅有同名节点时，写成 `NODE:订阅/节点名`（订阅有简称就用简称）。已不存在的节点如果和现存节点同名，也会带上它原来的订阅名。打开时生成的去向文字，保存时只要没改，就沿用原来记下的节点，不再按名字查找，所以不会因为同名或改名而指错；写法和打开时某一行完全相同的去向，也指向同一个节点。新写或改过的节点去向必须能唯一找到一个节点，否则不能保存。
  - 保存前给出预览：新增、删除、修改的条数和顺序是否有变，列出将删除的例外、每个去向代表什么，以及有问题的行和原因（不认识的类型、重复、找不到或有歧义的节点、不认识的地区或去向）。有问题的行没处理好就不能保存；不认识的去向可以一键改为跟随主出口。
  - 已有例外按"类型 + 内容"对应，保存后保持原来的身份，连接列表里"命中例外 #n"不会错乱。如果编辑期间例外列表被别处改过（比如从连接列表加了一条），不会直接覆盖：用户没动过的行换成最新内容，别处新加的例外补在末尾，用户改过的行保持不变，再请用户检查后保存。
- **复制为规则。** 单条例外可以复制成上面的一行文本，粘回文本编辑能原样还原。
- **走向。** 与分流项的走向选项相同。
- **从连接列表生成。** 在一个连接上右键，选择"以后……走"，可以选择作用范围：
  - 只针对这个域名；
  - 整个主域名，用公共后缀表判断；
  - 这个 IP；
  - 这个程序。

  再选走向，就生成一条例外，并立即生效。

### 4.5 测试网址

输入一个网址、域名或 IP，界面告诉你：

> 命中「AI 服务」（来源：MetaCubeX category-ai-!cn）→ 美国·自动 → 当前是「洛杉矶 02 · 机场A」，140ms

旁边有一键操作：「改为直连」「改为主出口」「改为……」，点了就生成一条例外。

- 如果需要按 IP 判断，就先解析域名，并标注"按解析结果"。
- 端口和进程类规则没法用网址测试，标注"不适用"即可。
- 未连接时也能测试，只是不显示当前实际节点。

### 4.6 连接列表、首页、托盘

- **连接列表。** "命中规则"一列显示用户能看懂的名字："AI 服务""例外 #3""兜底""局域网"，不显示内核的原始规则文本。出口一列显示节点；遇到重名节点时附上订阅名。右键菜单里有"以后……走"，见 4.4。
- **首页。** 当前出口卡显示主出口及实际使用的节点。
- **托盘面板。** 显示主出口，可以快速切换：自动、地区自动、最近用过的节点。节点重名时附上订阅名。

### 4.7 方案

可用的方案有三种：

| 方案 | 来源 | 更新 | 结构能否修改 |
|---|---|---|---|
| 内置推荐 | 应用自带 | 随应用版本更新 | 能改走向和开关；能在清单里添加自己的分流项 |
| 「机场X」的方案 | 订阅附带 | 跟随订阅刷新 | 同上 |
| 我的方案 | 用户另存 | 不自动更新 | 完全自由 |

**分流方案只能选一个。** 启用多个订阅只会叠加节点，不会叠加方案。原因是内核同一时间只有一张规则表，从上往下第一条命中的规则生效。如果把多个方案硬合并，排在前面的方案说了算，后面的大部分规则不会生效，用户却看不出来。

**会跟随更新的方案（内置推荐、订阅附带）：**

- 方案自带的分流项可以改走向、开关，但不能删除，也不能调整顺序。
- 用户自己添加的分流项会作为叠加层保留：可以排序、删除，用"放在 X 之前"锚定位置。如果锚点被方案删掉了，就放到兜底之前。
- 需要完全控制时，选「另存为我的方案」。

**订阅刷新、方案内容变了：**

- 用户对每个分流项设置的走向和开关，按分流项名保留。
- 新增的分流项默认"跟随主出口"，并提示一次："「机场A」的方案新增了 2 个分流项。"
- 被删掉的分流项也提示一次。

**切换方案：** 同名分流项的走向沿用。比较名字时忽略开头的 emoji 和空白，并且不区分大小写。比如"💬 AI 服务"和"AI 服务"会被当作同一个。

**来源订阅停用或删除：**

- 订阅停用：方案继续可用，因为已经下载的规则数据还在。方案栏提示"来源订阅已停用，不再更新"。
- 订阅删除：方案自动转成"我的方案（来自已删除的「机场A」）"。

**新导入带方案的订阅时：** 如果它是第一个订阅，就自动采用它的方案；否则不切换，只在订阅卡片上显示"附带分流方案 · 17 个分流项 [使用]"。

### 4.8 走向与节点选择

所有地方的走向下拉都是同一套选项：

```
跟随主出口（自动 · 当前 香港 03 · 机场A）
直连
拦截
地区自动        ▸  香港（12）  日本（8）  美国（10） …
指定节点        ▸  可搜索的列表，按订阅分段：节点名 · 延迟
```

**主出口**可以是：

- 自动：所有可以参与自动选择的节点里最快的那个；
- 地区自动；
- 指定节点。

**地区自动：**

- 选该地区里最快的节点。如果该地区只有一个节点，就直接用它。
- 订阅刷新、节点改名、换密码都不受影响。这是推荐给大多数人的选项。

**指定节点：**

- 订阅刷新后按"订阅 + 节点名"找回（第 7 节）。
- 默认打开"不可用时临时用同地区最快的节点"。被临时替换时，在节点页和托盘提示："你为「AI 服务」指定的「东京 03 · 机场A」不可用，临时使用「东京 05 · 机场A」。"
- 如果节点已经从订阅里消失，同样临时用同地区最快的节点，并提示 [重新选择] [知道了]。指定的节点不会被静默清除。

**节点页：**

- 顶部是主出口条：自动卡片、地区自动卡片、当前指定的节点。卡片放不下的地区，在"更多地区"菜单里仍然可以选。
- 主出口条下面有一行"分流项正在使用"，列出走向不是"跟随主出口"的分流项及其实际节点，例如："AI 服务 → 洛杉矶 02 · 机场A（140ms）"。
- 筛选除了按地区，还可以按订阅。
- 节点卡片上始终显示订阅名（现在已经有）。
- 卡片右键菜单：
  - 设为主出口；
  - 用于分流项……；
  - 不参与自动选择；
  - 设置地区……（自动识别错误时手动更正）；
  - 复制名称。

**订阅设置**里增加两项："参与自动选择"开关（默认开），以及短别名，用于"节点名 · 订阅名"的显示。现有的按名字包含 / 排除节点的正则保留不变。

### 4.9 状态与提示

| 情况 | 提示方式 |
|---|---|
| 某个来源更新失败 | 分流项那一行显示「N 天未更新」，继续使用上一份 |
| 某个分流项完全没有数据 | 行上显示「暂不可用」，生成配置时跳过它，不阻止连接；如果是启用中的分流项，连接后提示一次 |
| 部分规则不支持 | 行上显示「部分规则不支持」，详情里列出类型和条数 |
| 指定节点被临时替换或已消失 | 节点页横幅，加一次通知 |
| 订阅方案的分流项有增减 | 提示一次 |

## 5. 规则来源与格式

### 5.1 sing-box 本身支持什么

sing-box 1.14.4 的规则集只支持两种格式：`source`（JSON）和 `binary`（.srs）。自带的转换工具只能处理 AdGuard 列表。Clash 的 yaml/list、mihomo 的 .mrs、Surge 的 list、geosite.dat 都不能直接使用。所以**格式支持全部由客户端负责**。

### 5.2 统一的处理流程

所有来源都走同一条流程：

1. **下载**：见 5.5。
2. **识别格式**：看内容，不依赖扩展名。
3. **解析**：解析成内部的统一条目列表。
4. **分成两部分**：域名部分（域名 / 后缀 / 关键字 / 正则，以及进程、端口等不需要先解析域名的条件）和 IP 部分。
5. **合并编译**：把同一分流项的所有来源合并，并编译成内核支持的 .srs 版本。每个分流项最多生成两个资源，一个域名部分、一个 IP 部分。
6. **存储并交给 agent**：编译结果按内容寻址存储，作为 `res:` 资源交给 agent。

这条流程同时解决了三个问题：

- **格式差异。**
- **.srs 版本兼容。** 读入任何版本，都按当前内核的版本重新写出。
- **资源数量上限。** 一个订阅方案里的 47 个规则集，合并成 17 个分流项之后，最多 34 个资源。

内部条目列表也保存在客户端，供"测试网址"做本地匹配。

### 5.3 支持的格式

| 格式 | 识别方式 | 处理 |
|---|---|---|
| sing-box .srs | 文件头 `SRS` | 读取后重新编译 |
| sing-box JSON（source） | 含 `version` 和 `rules` | 解析 headless rule，包括 logical 规则 |
| Clash rule-provider YAML | 含 `payload` | 按 behavior 处理：domain / ipcidr / classical。行为未知时根据内容推断 |
| Clash / Surge 文本列表 | 每行 `TYPE,value[,…]` | 按 classical 处理 |
| 纯域名列表 / Surge DOMAIN-SET | 每行一个域名 | 见下方的点号规则 |
| 纯 IP 段列表 | 每行一个 CIDR | 作为 IP 部分 |
| AdGuard / Adblock 过滤列表 | `\|\|example.com^` 这种写法 | 只取域名拦截条目，与 sing-box 的 adguard 转换语义一致 |
| hosts 文件 | `0.0.0.0 example.com` | 取出域名 |
| mihomo .mrs | 文件头 `MRS` | 见 5.4 |

**点号规则（实现时必须用测试确认）：**

- Clash 的域名写法：`+.a.com` 表示 a.com 及其所有子域名；`.a.com` 只表示子域名；`*.a.com` 只表示一级子域名，转成正则。
- Surge 的 DOMAIN-SET 写法：`.a.com` 表示 a.com 及其所有子域名。
- 无法判断来自哪种软件时，根据来源提示决定：已知项目、或路径里包含 `surge`/`clash`。都没有时按 Clash 处理。

**Clash classical 类型的转换：**

| Clash | sing-box |
|---|---|
| DOMAIN / DOMAIN-SUFFIX / DOMAIN-KEYWORD / DOMAIN-REGEX | domain / domain_suffix / domain_keyword / domain_regex |
| DOMAIN-WILDCARD | domain_regex |
| IP-CIDR / IP-CIDR6 | ip_cidr（IP 部分）。`no-resolve` 忽略，因为 IP 部分本来就排在后面 |
| SRC-IP-CIDR / SRC-PORT / DST-PORT | source_ip_cidr / source_port / port、port_range |
| PROCESS-NAME / PROCESS-PATH | process_name / process_path |
| NETWORK | network |
| GEOSITE,x / GEOIP,x | 展开成 MetaCubeX 对应名字的数据，并入当前来源 |
| IP-ASN,n | MetaCubeX 的 `asn/ASn.srs` |
| AND / OR / NOT | logical 规则（NOT 转成 invert） |
| USER-AGENT、URL-REGEX、IN-PORT、SUB-RULE 等 | 不支持，计数并在详情里列出 |

### 5.4 mihomo .mrs

常见的 .mrs 来源，都能在同一个项目里找到同名的 sing-box 版本。客户端内置一张对应表，例如：

- MetaCubeX：`meta/geo/geosite/x.mrs` 对应 `sing/geo/geosite/x.srs`，geoip 同理；
- DustinWin：`mihomo-ruleset` 对应 `sing-box-ruleset`；
- Loyalsoldier/geoip：mrs 对应 srs。

遇到不在表里的 .mrs，标为"暂不可用"，并提示用户换一个 sing-box 或 Clash 文本格式的链接。是否自己实现 .mrs 解码，放到以后再定；实现前需要先确认 mihomo 代码的许可证。

### 5.5 下载与镜像

- **由谁下载。** 下载由 GUI 进程完成，agent 不联网。
- **已连接时**，下载请求本身就经过 TUN 和分流规则，能正常访问 GitHub。
- **未连接时**，按顺序尝试：GitHub 原始地址 → jsDelivr（仅限 GitHub 仓库文件）→ 用户设置的自定义镜像前缀。
- **镜像前缀。** 订阅里常见形如 `https://某镜像/https://github.com/…` 的地址，先剥掉前缀，按真实来源去下载，不依赖第三方镜像。
- **下载限制。** 单个文件最大 32 MiB，并且必须能正确解析，否则视为失败，保留上一份。
- **首次连接时缺数据**，沿用现在的做法：最多等 25 秒；拿不到数据的分流项暂时跳过，并提示用户。

### 5.6 更新

- **每个来源独立记录**：更新时间、ETag、内容哈希。
- **默认更新频率**：每 24 小时检查一次（现在是 72 小时，规则集通常每天更新）。可以在设置里调整。
- **内容变化时**重新编译受影响的分流项。连接中按现有的"刷新后重新应用"设置决定是否立刻应用。
- **同一个文件只下载一次。** 多个方案或多个分流项引用同一个文件时，共用一份。

### 5.7 内置规则目录

目录随应用发布。它只包含名字、说明和下载地址，不包含规则数据本身，所以不涉及重新分发规则数据。目录分为三部分：

**1. 精选条目，约 60 到 100 个。** 每个条目包括：

- 标识、中英文名称、图标；
- 搜索用的别名，例如"奈飞""网飞"都指向 Netflix；
- 类别：拦截、AI、流媒体、社交、通讯、开发、游戏、云、金融、国内、海外；
- 推荐来源，以及若干备选来源；
- 默认走向、默认插入优先级。

**2. 名称快照。** 包括 MetaCubeX geosite（约 4000 个名字）和 blackmatrix7 Clash 分类（约 670 个名字），随应用版本更新。

**3. 收录的项目：**

| 用途 | 项目 | 格式 |
|---|---|---|
| 基础数据（默认） | MetaCubeX/meta-rules-dat（sing 分支） | .srs：geosite、geoip（含服务 IP）、ASN |
| 基础数据（备选） | SagerNet/sing-geosite、sing-geoip；Loyalsoldier/geoip；DustinWin/ruleset_geodata | .srs |
| 按服务分类 | blackmatrix7/ios_rule_script；Loyalsoldier/clash-rules；ACL4SSR | Clash，需要转换 |
| 按服务分类 | SukkaW/Surge（ruleset.skk.moe）；VPSDance/ai-proxy-rules | sing-box JSON |
| 去广告 | anti-AD；217heidai/adblockfilters；秋风 AWAvenue | .srs / JSON |
| 去广告 | hagezi/dns-blocklists | Adblock 格式，需要转换 |

## 6. 订阅附带的方案

### 6.1 导入时取什么、不取什么

**要取的：**

- 节点（现有逻辑）；
- 分组和规则，转成分流项、走向和兜底；
- 规则集引用，转成来源。

**一律忽略的：**

- DNS、fake-ip；
- 入站、端口、TUN；
- `geox-url`、`mode`、日志、实验项。

这些本机设置由应用管理。如果照搬，会和应用的连接管理冲突，也会突破 agent 的安全策略。

### 6.2 规则如何变成分流项

- **按目标分组聚合。** 指向同一个分组的规则合成一个分流项，名字取分组名，位置取这个分组第一次出现的位置。它的来源包括：引用的规则集，加上直接写在规则里的条目（作为一个内嵌来源）。
- **拦截类规则。** sing-box 的 `action: reject`，或 Clash 里指向 `REJECT` 的规则（以及默认成员是 REJECT 的分组），变成走向为"拦截"的分流项。
- **兜底。** sing-box 的 `route.final`，或 Clash 的 `MATCH`，变成兜底的走向。
- **局域网规则。** sing-box 的 `ip_is_private`、private 规则集，或 Clash 的 `GEOIP,private`，对应应用自己的"局域网直连"层，不重复生成分流项。
- **忽略的规则。** `sniff`、`hijack-dns`、`clash_mode` 等，由应用自己生成。
- **排序例外。** 如果同一个分组的规则被其他分组的规则隔开，比如 A、B、A，合并后 A 只出现一次。这会让少数规则的先后顺序稍有变化，导入时在分流项详情里注明。

### 6.3 分组如何变成走向

| 分组的样子 | 映射为 |
|---|---|
| select，成员是"主选择组 + 全部节点 + 直连"（最常见的结构） | 默认成员是什么就映射成什么。sing-box 看 `default`，没有就取第一个成员；Clash 取第一个成员。主选择组映射为"跟随主出口"，DIRECT 映射为"直连"，REJECT 映射为"拦截" |
| 方案的主选择组本身（规则里的最终出口） | 主出口。它的默认成员决定主出口初始值：自动选择组映射为"自动"，指定节点映射为"指定节点" |
| url-test / urltest，成员都属于同一个地区 | 该地区自动 |
| url-test，成员跨多个地区 | 跟随主出口，并在详情里注明"原方案为多地区自动选择" |
| select 只包含部分节点 | 默认成员是节点就映射为"指定节点"，否则按上面的规则处理 |
| fallback / load-balance | 地区一致时映射为地区自动，否则跟随主出口，并注明 |

### 6.4 实例

以一个真实的 sublink 生成订阅为例。它的 sing-box 版和 Clash 版结构一致：

- 6 个节点；
- 分组："🚀 节点选择"（主选择）、"⚡ 自动选择"，以及 17 个服务分组；
- 规则：47 条规则全部引用 MetaCubeX 的规则集，兜底是"🐟 漏网之鱼"。sing-box 版引用 .srs，Clash 版引用 .mrs，并且都套了第三方镜像前缀。

导入后，两种格式都应该得到同样的结果：

- 17 个分流项，顺序与原方案一致；
- "🔒 国内服务"和"🏠 私有网络"的默认成员是 DIRECT，所以前者走向为"直连"，后者归入局域网直连层；
- 其余分流项"跟随主出口"；
- 兜底"跟随主出口"；
- 广告：sing-box 版里是直接拦截，Clash 版里是一个分组。两种都映射成走向为"拦截"的分流项。

这个例子要作为验收用例（第 12 节）。

## 7. 节点身份

- **身份由什么构成**：订阅 ID + 节点名，同一订阅里出现重名时再加序号。另外记录节点配置的哈希和最后一次识别到的地区，作为兜底信息。
- **订阅刷新后找回的顺序**：先按"订阅 + 名字"找；找不到就按哈希找（应对改名但配置没变的情况）；还找不到，就视为"已消失"，按 4.8 处理。
- **用到身份的地方**：主出口、分流项走向、"不参与自动选择"、手动设置的地区，都保存这个身份，而不是生成配置时的 tag。
- **tag 只在配置内部使用**：生成配置时，tag 仍然从名字派生并保证唯一，但不对外暴露。

## 8. 生成配置

### 8.1 出口结构

- **主出口**：一个选择器（沿用现在的 `Proxy`），成员包括：自动、各地区自动、全部节点。
- **自动、地区自动**：沿用现在的 urltest 组。成员排除"不参与自动选择"的节点和关闭了"参与自动选择"的订阅。地区自动组为所有至少有一个节点的地区生成。
- **每个分流项一个选择器**，成员包括：主出口、直连、各地区自动、全部节点。这样在"跟随主出口 / 直连 / 地区自动 / 指定节点"之间切换时，通过选择接口在运行时完成，不需要重启内核。配置摘要不包含各选择器的当前选择（现在已经这样处理主出口）。
- **走向为"拦截"**：生成 `action: reject` 规则。切换到"拦截"或从"拦截"切走，需要重新生成配置，这类操作很少，可以接受。
- **指定节点 + 不可用时临时替换**：sing-box 没有"首选某节点、不可用时切到备用"的组类型。需要在项目 fork 的 `urltestgroup` 里增加这种行为：首选节点健康时用它，否则用同地区里最快的节点。新类型要在 agent 的策略白名单里登记。这件事必须放在 agent 侧做，因为 GUI 关闭后仍要生效。

### 8.2 规则顺序

| 层 | 内容 |
|---|---|
| 0 | sniff、DNS 劫持、Direct / Global 模式（现有） |
| 1 | 局域网直连（开关，默认开） |
| 2 | 我的例外，按列表顺序；在第一条 IP 类例外之前插入一次 resolve |
| 3 | 各分流项的域名部分，按方案顺序 |
| 4 | resolve：只在后面还有 IP 部分时才插入 |
| 5 | 各分流项的 IP 部分，按方案顺序 |
| 6 | 兜底 |

把所有分流项的域名部分排在所有 IP 部分之前，和 Clash 方案常见的 `no-resolve` 写法效果一致：命中域名的流量不会多做一次 DNS 解析。

### 8.3 DNS

- **只用域名部分生成 DNS 规则**：走向是"直连"的用国内 DNS，"拦截"的直接拒绝，其余用远程 DNS。
- **IP 部分不参与 DNS 规则**，避免 IP 类规则集在 DNS 阶段的匹配问题。
- **DNS 兜底**：兜底走向是"直连"时用国内 DNS，否则用远程 DNS。
- 其余与现有 DNS 设计一致。

### 8.4 agent 侧的调整

- **资源数量上限**：从 64 个提高到 256 个。单个文件 16 MiB、总计 64 MiB 的大小上限不变。
- **新的组类型**：在策略白名单里登记 8.1 提到的"首选 + 备用"组类型。
- 其他安全边界不变：只接受 `res:` 本地规则集，不接受远程规则集，agent 不联网。

## 9. 内置推荐方案

数据来源统一用 MetaCubeX/meta-rules-dat 的 sing 分支。选它的原因：

- 它有 Telegram、Google、Netflix 等服务的 IP 段，官方 sing-geoip 只有国家维度的数据；
- 每天更新；
- 和大量订阅模板用的是同一套名字，订阅方案和内置方案引用同一个文件时，只需要下载一次。

| # | 分流项 | 来源（geosite / geoip） | 默认走向 | 默认开启 |
|---|---|---|---|---|
| 1 | 广告拦截 | geosite category-ads-all | 拦截 | 否 |
| 2 | AI 服务 | geosite category-ai-!cn | 跟随主出口 | 是 |
| 3 | Telegram | geosite telegram；geoip telegram | 跟随主出口 | 是 |
| 4 | YouTube | geosite youtube | 跟随主出口 | 是 |
| 5 | 流媒体 | geosite netflix、disney、hbo、primevideo、spotify；geoip netflix | 跟随主出口 | 是 |
| 6 | Google | geosite google；geoip google | 跟随主出口 | 是 |
| 7 | 社交媒体 | geosite twitter、facebook、instagram、tiktok；geoip twitter、facebook | 跟随主出口 | 是 |
| 8 | GitHub | geosite github | 跟随主出口 | 是 |
| 9 | 微软 | geosite microsoft | 直连 | 是 |
| 10 | 苹果 | geosite apple | 直连 | 是 |

## 10. 从现有版本迁移

升级后第一次启动时，自动执行一次迁移：

| 现有设置 | 迁移为 |
|---|---|
| 路由预设：国内直连（`china`） | 内置推荐方案 |
| 路由预设：全部代理（`proxy-all`） | 内置推荐方案，"国内网站"改为"跟随主出口" |
| 路由预设：仅代理国外（`foreign-only`） | 内置推荐方案，兜底改为"直连" |
| 拦截广告（`BlockAds`） | 开启"广告拦截"分流项 |
| 局域网直连（`LANDirect`）、IPv6 | 移到设置页的"网络"部分，含义不变 |
| 自定义规则 | 按原顺序变成"我的例外"。代理映射为"跟随主出口"，直连映射为"直连"，拒绝映射为"拦截" |
| `SelectedNode` 是节点哈希 | 按哈希找到节点，转成节点身份，作为主出口的指定节点；找不到就设为"自动"，并提示一次 |

| 地区分组开关（`RegionGroups`） | 删除，地区自动始终可选 |
| 规则数据镜像、更新频率 | 保留 |

已经下载的 SagerNet 规则数据不再使用。新方案需要的数据，在第一次连接前按 5.5 的方式下载。

## 11. 约束

- **订阅内容按凭据对待。** 包括节点名、服务器和分组成员。日志、诊断报告、测试输出里都只记录数量和类型。用真实订阅做的测试，必须显式开启才运行，订阅链接通过文件路径传入，不能进仓库。
- **规则集链接和规则内容不是机密**，可以正常记录。但链接里的镜像前缀不能用来推断用户身份；带查询参数的链接，在显示和诊断报告里隐藏参数。
- **GUI 只交资源，不交下载地址。** GUI 交给 agent 的配置里，规则集一律是本地资源；agent 依然拒绝远程规则集。
- **数据格式要标版本。** 新的数据结构（方案、分流项、来源、例外、节点身份）都要带版本号，迁移只能执行一次，而且必须可以重复执行而不出错。

- 第 6.4 节的真实订阅，sing-box 链接和 Clash 链接得到相同的 17 个分流项和相同的走向。这项测试要显式开启才运行，日志只记录数量；
- 同时启用两个带方案的订阅时，只有一个方案生效，节点合并显示；
- 订阅刷新后方案增减了分流项，用户的走向选择保留，并有提示。

### 阶段四：使用体验

**内容：**

- 测试网址；
- 从连接列表生成例外；
- 例外和手写分流项的批量粘贴（带预览），包括 Clash 写法；
- "首选节点 + 同地区备用"的组类型；
- 不参与自动选择；
- 手动设置地区；
- 连接列表显示易懂的命中原因；
- 托盘重名节点加订阅名。

**验收：**

- 测试网址的结果和真实连接命中的规则一致，用一组域名和 IP 对照验证；
- 首选节点断开后，流量自动切到同地区的其他节点，恢复后切回。

## 13. 已定决策

| 决策 | 理由 |
|---|---|
| 同一时间只有一个分流方案生效，节点可以叠加 | 内核只有一张规则表，合并多个方案会造成看不见的冲突 |
| 默认数据源用 MetaCubeX meta-rules-dat sing 分支 | 有服务 IP 段、每日更新、和订阅模板命名一致 |
| 客户端把所有格式统一编译为 .srs | sing-box 只支持 srs 和 JSON；同时解决版本兼容和资源数量问题 |
| 订阅方案只取分类和规则，不绑定这个订阅的节点 | 常见模板的分组本来就是"主选择 + 全部节点 + 直连"，不丢信息；而且跨订阅可用 |
| 第一个订阅带方案时自动采用，之后不自动切换 | 让导入即可用，同时避免后来的订阅打乱用户已经调好的方案 |
| 广告拦截默认关闭 | 和现在一致；误拦截比漏拦截更伤用户体验 |
| 微软、苹果默认直连 | 国内能直接访问，直连下载更快；和常见模板一致 |
| 每个分流项一个选择器 | 改走向不需要重启内核，符合 `design.md` 里"切换节点优先调用选择接口"的原则 |
| 跟随更新的方案不能删除自带分流项，也不能调整它们的顺序 | 订阅刷新时能可靠地合并用户的修改；需要完全控制就另存为我的方案 |

## 14. 实现中与本文不同的地方

实现和验证中发现，以下几处照搬本文行不通，或者有更好的做法。已按下面的方式实现。出现差异时，以代码和本节为准，上文保持原样。

1. **广告分组的导入（6.3）。** 本文说分组由默认成员决定走向。但订阅模板里的广告分组，常常是"默认成员是节点选择组，REJECT 只是其中一个选项"，照此会变成"跟随主出口"，广告就拦不住了。所以：明显用来拦广告的分组（名字像广告拦截，或它的规则全部来自去广告规则集），只要成员里有 REJECT，就导入为"拦截"；其他分组仍然只看默认成员。
2. **"首选节点 + 同地区备用"（8.1）。** 实现成 fork 的 `urltestgroup` 里的一种出站类型 `preferred`，不改 agent 接口的 proto。限制：正在拨向坏节点的那条连接会失败一次，之后的新连接才使用备用节点，内核做不到更平滑。
3. **DNS 服务器怎么选（8.1、8.3）。** 8.3 说按走向选 DNS，8.1 又要求在直连、地区自动、指定节点、跟随之间切换时不重启内核，两者互相矛盾。实现是：分流项用哪个 DNS，由它自身的固有属性（是不是国内）决定，不随当前走向变，这样所有切换都是运行时切换。代价：国内分流项被改成走节点时，仍然向国内 DNS 解析。
4. **测试网址（4.5）。** 查不到的域名拒绝作答，和内核的行为一致，不猜结果；连接处于全局或直连模式时，按模式回答，而不是按方案。
5. **重复的例外（4.4）。** 添加一条已有的例外，是更新那一条，不重复列出。
6. **界面措辞。** 本文示例里的文案，界面里用了自己的措辞，例如"尚未就绪"对应本文的"暂不可用"。行为按本文。
7. **规则目录的规模（5.7）。** MetaCubeX geosite 的名称快照是 2019 个名字，两种格式（.srs、.mrs）共 4038 个文件，不是"约 4000 个名字"。
8. **内置推荐方案的条数（4.2、9）。** 是第 9 节表里的 12 个分流项，加兜底。4.2 示例里的"13 个分流项"只是示意。
9. **规则集预览（4.3）。** 区分"链接被换成了可读的真实地址"和"内容被转换了格式"两种情况，预览里各有一句说明。

## 15. 解析方式与按环境切换

本节是在第 14 节之后加的一轮设计。它改变了 8.2 的局域网直连和 8.3 的 DNS 选择。和上文冲突的地方，以本节为准。

### 15.1 为什么要改

一类常见需求：某个内部网络的域名只有它自己的 DNS 能解析，而用户会从不同的地方访问它。例如：

- **直接接入时**：内部域名直连，必须用内部 DNS 解析。公网直连的域名照常用国内 DNS，走代理的用远程 DNS。
- **不在这个网络里时**：内部域名和内部地址段都交给一个能进入这个网络的代理节点。这些域名在公网上查不到，只能由节点那一端去解析。

现有设计做不到，原因有三：

1. 只有「国内 DNS」「远程 DNS」两个服务器，不能按规则指定解析用的服务器。
2. 走节点的域名一律经主出口向远程 DNS 解析。内网域名在公网上查不到，TUN 模式下应用拿不到地址，连接根本发不出去。
3. 「局域网直连」排在所有规则前面，「某个私有地址段 → 某个节点」这样的规则永远不会生效。

而且这些设置要能**随规则一起切换**：换环境时只开关几个分流项，不用去设置页改 DNS。

### 15.2 解析方式

凡是有走向的地方（每条例外、每个分流项），都可以设置**解析方式**。它决定这条规则匹配的域名用哪个 DNS 服务器解析。取值和含义在两处完全相同：

| 文本写法 | 界面名称 | 含义 |
|---|---|---|
| 不写 | 默认 | 和现在一样：分流项按 8.3 和第 14 节第 3 条选择；例外是直连的用国内 DNS，其余用远程 DNS |
| `dns=<服务器>` | 指定服务器 | 用这个服务器解析，查询**经过这条规则自己的出口**。服务器的写法和设置页的 DNS 相同：`10.0.0.53`、`udp://…`、`tcp://…`、`tls://…`、`https://…`，以及 `system`（系统当前的 DNS）。保存时统一成一种写法（`udp://1.1.1.1:53` 存成 `1.1.1.1`，`TLS://DNS.x:853` 存成 `tls://dns.x`，IPv6 地址用小写的标准写法），写法不同但指的是同一个服务器，就算同一个 |
| `dns=exit` | 由出口解析 | 本地不解析：只对这条规则的域名返回 fake-ip 地址，连接时再换回域名，交给出口那一端解析 |

- **例外**：写在文本行的末尾，例如 `DOMAIN-SUFFIX,corp.example,DIRECT,dns=10.0.0.53`、`DOMAIN-KEYWORD,intra,NODE:Gateway,dns=exit`。可以和 `no-resolve` 一起写，也可以不写去向（`DOMAIN-SUFFIX,a.com,dns=exit` 表示跟随主出口、由出口解析）。「复制为规则」会带上它，粘贴回去能原样还原。
- **分流项**：在详情页「走向」下面设置，一个分流项一个值。手写条目和规则集来源都适用。
- **方案**：在跟随更新的方案里，解析方式像走向一样记在用户的叠加层上，按分流项的名字对应；刷新方案和切换方案时会保留，「恢复默认」会清除它。
- **校验**：服务器要么是 IP 地址，要么是带点的主机名（`localhost` 也可以）；`dns=exti`、`dns=sytem`、`dns=10.0.0.256` 这类笔误会被标出来，不会当成一台叫这个名字的服务器。设置页的 DNS 不受这条限制，和以前一样。IP 段、端口、程序这类规则不查 DNS，写了 `dns=` 时保存预览会把这一行标为有问题，原因是这个选项在这里不起作用。服务器写错了也标出来。只改 `dns=` 也算「修改」，例外原来的身份不变。在分流项的手写条目里粘贴带 `dns=` 的行，这一行会被标出来，不会悄悄丢掉：分流项的解析方式只在详情里设一次，对所有条目生效。
- **`system` 不经过出口**：系统 DNS 只能在本机查询。
- **走向是拦截时**，解析方式不起作用，这些域名的查询直接被拒绝。

**为什么不会冲突。** DNS 规则和路由规则按同一个顺序生成。一个域名由哪条规则决定走向，就由同一条规则决定用哪个 DNS。例外排在所有分流项前面，所以例外的解析方式也排在前面。

### 15.3 生成配置

- **指定服务器**：每个不同的「服务器 + 出口」组合生成一个 DNS 服务器。出口是分流项的选择器，所以在运行时切换走向，DNS 查询会跟着切换，不用重启内核。例外的出口是固定的；直连不设 `detour`，因为 sing-box 不允许 detour 到一个空的 direct 出站。
  - 走代理时，UDP 查询要求节点支持 UDP；不支持的节点用 `tcp://`。
  - 服务器写成域名时，用国内 DNS 解析它（国内 DNS 设成 `system` 时，在内网里就能解析内网的名字），不用公共的引导 DNS，以免把内网名字发给公共服务器。内网 DNS 最好直接写成 IP。
  - 以域名形式到达内核的连接（经本地 HTTP/SOCKS 代理端口）不会先查 DNS，直连出站会用国内 DNS 解析。所以在这条规则的路由规则之前，再加一条只对它的域名生效的 `resolve`，指定同一个服务器。以 IP 形式到达的连接（TUN）不受影响。排在例外之间那次 resolve 之后的规则不需要再加：那次 resolve 已经按 DNS 规则用这个服务器解析过。
- **由出口解析**：用 fake-ip 服务器（IPv4 `198.18.0.0/15`，开了 IPv6 时再加 `fc00::/18`）回答，并开启缓存文件的 `store_fakeip`，让内核重启后仍能认出旧的 fake-ip 地址。
  - fake-ip 服务器**只在有规则用它时**才写进配置。它在配置里时，内核会把这个网段里的所有地址都当成 fake-ip，这个网段里真实存在的主机就连不上了。
  - fake-ip 的回答 TTL 改写成 1 秒（内核默认是 10 分钟）。换环境、关掉最后一个「由出口解析」的分流项后，程序很快会重新查询并拿到真实地址，不会长时间拿着一个已经没有服务器能换回域名的 fake-ip。这些域名的 A/AAAA 查询返回 fake-ip，其他类型的查询返回空的 NOERROR，不能返回 NXDOMAIN，否则系统会认为这个名字不存在。
  - 内核只对客户端发来的查询使用 fake-ip，自己的解析（resolve、直连出站解析域名）会跳过 fake-ip 规则，这正是需要的行为。
  - 内核的 resolve 动作解析失败时会断开连接。所以例外之间插入的那次 resolve 要跳过这些域名，否则一条排在前面的 IP 类例外会让内网域名在 resolve 这一步就失败。跳过的条件和 DNS 规则的判断完全一致：在它后面的规则里，**第一条**匹配这个域名的规则是「由出口解析」，才跳过；如果更早的一条规则给这个域名指定了别的服务器，就照常解析。用逻辑规则写成：「在某个由出口解析的规则集里，并且不在它之前的任何其他规则集里」，取反。分流项 IP 部分之前的那次 resolve 不需要这个条件：能决定 DNS 的规则都在它前面，走到这里的域名一个都没匹配上。
  - 走向是直连时，「由出口解析」就是由直连出站解析，用的是国内 DNS。
- 没有规则设置解析方式、也没有认领私有段时，生成的配置和以前完全相同。

### 15.4 用户手写的私有地址段优先于局域网直连

「局域网直连」仍然排在最前面（8.2 的第 1 层），但**让出用户亲手写下的私有地址段**：

- **认领**：已启用并且**实际写进配置**的例外里的 IP 段，以及**实际写进配置**的分流项里**用户自己写的** IP 条目。订阅方案导入时带来的条目（例如机场模板里的 `IP-CIDR,192.168.0.0/16,DIRECT`）也是内联条目，但不算用户写的，不能认领。用户编辑这样的来源时，原来就有的私有段记为「继承的」，仍然不能认领；只有用户新加的段才算。来源上记一个「用户写的」标记；升级时（分流状态的格式 1 → 2，资料库文件的格式不变，旧版本仍能打开）给以前的手写来源补上标记，按来源编号的格式区分：用户写的来源编号是随机生成的，订阅导入的是按内容算的哈希。这一步每次读入都做（只补不删），所以退回旧版本又升级回来，旧版本丢掉的标记也会补回来。在旧版本里编辑过的订阅来源分不清哪些是用户加的，按订阅的算，不认领；用户编辑过的订阅来源在退回旧版本再升级后也是这样。规则里的 DNS 服务器不能写 `localhost`，本机请写 `127.0.0.1` 或 `::1`。还在等规则数据、或者因为资源上限没写进去的分流项，不会认领。只有完全落在局域网地址空间里的段才算（例如 `10.0.0.0/8`、`192.168.50.0/24`）；`0.0.0.0/0` 这类只是覆盖到的不算。局域网地址空间和内核的 `ip_is_private` 一致。
- **生成**：没有认领时，规则和以前一样是 `ip_is_private → 直连`。有认领时，改成逻辑规则「是私有地址，并且不在认领的段里 → 直连」。被认领的地址交给后面的规则，按原来的顺序匹配。
- **规则集不能认领**：方案和规则集里的内容永远不能把局域网流量拿走。
- **被认领的地址按正常顺序匹配**：和其他 IP 规则一样，所有分流项的域名部分排在 IP 部分前面。一个被认领的私有地址连接，如果嗅探出的域名命中了排在前面的某个分流项的域名规则，就按那个分流项走。所以这类分流项应该放在宽泛的方案分流项前面（在「我的方案」里可以调整顺序）。
- **测试网址**：按同样的规则回答（「有地址是私有的，并且没有地址被认领」，和内核的逻辑规则一致）。另外，第一条匹配某个域名的规则如果指定了自己的 DNS 服务器（`system` 除外，它就是测试网址自己用的解析），而本机的 DNS 解析不了这个域名，测试网址不会因此说「拒绝」，而是按域名继续匹配：那个服务器可能能解析，测试网址没法替内核去问它。

这样「一个小段 → 直连」写在前、「包含它的大段 → 某个节点」写在后，就能直接生效，不用关掉全局开关。

最初的设计是把局域网直连整个移到兜底之前。验证时发现这样会出问题：方案里的规则会抢走局域网流量。端到端测试里，`127.0.0.1` 命中了内置方案的「国内」IP 列表。实际使用中，一个经内部 DNS 解析到私有地址的域名，或者路由器管理页的域名，会被方案里宽泛的域名规则送去代理。所以改成现在这样，只让用户自己写的规则优先。测试网址（4.5）按同样的规则回答。

### 15.5 按环境切换：开关分流项

切换环境不加新概念：基于内置方案「另存为我的方案」，加几个手写分流项，每个设好走向和解析方式，在不同环境下开关对应的分流项即可。例如：

| 分流项 | 走向 | 解析方式 | 内容 |
|---|---|---|---|
| 内部网络 · 直接接入 | 直连 | 内部 DNS 的 IP，或 `system` | 内部域名 |
| 内部网络 · 经节点 | 能进入该网络的节点 | 由出口解析 | 内部域名、内部地址段 |

例外是全局的，并且排在所有分流项前面，所以随环境变化的规则不应该写在例外里。为此加一个**覆盖提示**：分流项的手写条目被某条已启用的例外完全覆盖时（同一条，或者例外的后缀、关键词、IP 段包含它），详情页提示「被例外 #n 覆盖」，并说明走向和解析方式都以例外为准。只比较手写条目；规则集来源的内容不展开比较。

### 15.6 系统路由：验证结论，暂缓

原先设想加一个「系统路由」走向，让经其他组网工具或 VPN 的地址不进入 TUN、由系统路由表处理。按 sing-box 1.14.4 的源码验证：

- 开启 `auto_detect_interface` 时，出站连接绑定的网卡是**自身子网包含目标地址的那块网卡**（`interfaceFinder.ByAddr`），找不到时才用默认网卡。所以目标在组网工具自己的子网里，或者节点地址在这个子网里，用普通的直连就能走通，不需要系统路由。
- 只有**经路由而非同一子网**到达的地址（例如另一个 VPN 推送的一个大段路由，网卡地址不在这个段里）才会被错绑到默认网卡。

这种情况比原先设想的少，并且要改 TUN 路由，每次开关都要重建 TUN。所以先不做，等有具体场景再加。设计保留：作为一种走向，只接受 IP 段，写进 TUN 的 `route_exclude_address`。

### 15.7 暂不做

- 托盘里直接开关「我的方案」的分流项。
- 粘贴一段带不同去向的规则（例如其他代理工具配置里的规则段），按去向自动拆成几个分流项。

### 15.8 验收

- 例外文本：`dns=` 的读、写、往返，和 `no-resolve`、`NODE:`、正则、引号一起使用；错误值和非域名规则上的 `dns=` 都在预览里标出；只改 `dns=` 计为修改，身份不变。
- 分流项：在我的方案和跟随更新的方案里设置、清除解析方式；切换方案和刷新方案时保留；另存为我的方案时带上。
- 生成配置：默认解析方式的输出不变；指定服务器的 DNS 服务器和 detour 正确（直连不设 detour，分流项指向自己的选择器）；以域名到达的连接也用这个服务器解析；fake-ip 只作用于对应的域名；resolve 规则排除由出口解析的域名；局域网直连让出用户认领的私有段，其他私有地址照旧直连；真实内核能加载生成的配置。
- 测试网址按新的顺序回答。
- 界面：分流项详情和单条例外对话框能设置解析方式，两种语言；编译后没有域名规则的分流项（或者还没编译、只有手写 IP、端口、程序条目的分流项）不显示这个设置；从「添加例外」再次添加已有的匹配，不会清掉它的解析方式；把例外改成拦截时保留它的解析方式；分流项菜单里的「恢复方案的选择」也恢复解析方式；覆盖提示能显示。
