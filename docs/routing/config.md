# 生成配置

本文讲 GUI 怎样把方案、例外、走向和解析方式变成交给 agent 的 sing-box 配置：出口结构、规则顺序、局域网直连与认领、DNS（含按规则指定的服务器和 fake-ip），以及 agent 侧为此做的调整。

不在本文：用户怎样设置走向和解析方式见 [用户体验](experience.md)；规则数据怎样下载和编译成 .srs 见 [规则来源](rule-sources.md)；"用户写的"标记怎样保存和迁移见 [数据与迁移](data-and-migration.md#3-分流状态格式-2用户写的标记)；节点身份和 tag 的关系见 [节点](nodes.md#1-节点身份)。

## 1. 出口结构

- **主出口**：一个选择器（沿用原来的 `Proxy`），成员包括：自动、各地区自动、全部节点。
- **自动、地区自动**：沿用原来的 urltest 组。成员排除"不参与自动选择"的节点和关闭了"参与自动选择"的订阅。地区自动组为所有至少有一个节点的地区生成。
- **每个分流项一个选择器**，成员包括：主出口、直连、各地区自动、全部节点。这样在"跟随主出口 / 直连 / 地区自动 / 指定节点"之间切换时，通过选择接口在运行时完成，不需要重启内核。配置摘要不包含各选择器的当前选择（主出口原来就是这样处理的）。
- **走向为"拦截"**：生成 `action: reject` 规则。切换到"拦截"或从"拦截"切走，需要重新生成配置，这类操作很少，可以接受。
- **指定节点 + 不可用时临时替换**：sing-box 没有"首选某节点、不可用时切到备用"的组类型。所以在项目 fork 的 `urltestgroup` 里增加了一种出站类型 `preferred`：首选节点健康时用它，否则用同地区里最快的节点。它不改 agent 接口的 proto，新类型在 agent 的策略白名单里登记（第 4 节）。这件事必须放在 agent 侧做，因为 GUI 关闭后仍要生效。
  - 限制：正在拨向坏节点的那条连接会失败一次，之后的新连接才使用备用节点，内核做不到更平滑。

## 2. 规则顺序

| 层 | 内容 |
|---|---|
| 0 | sniff、DNS 劫持、Direct / Global 模式（原有） |
| 1 | 局域网直连（开关，默认开），让出用户认领的私有地址段，见 2.1 |
| 2 | 我的例外，按列表顺序；在第一条 IP 类例外之前插入一次 resolve（跳过由出口解析的域名，见 3.2） |
| 3 | 各分流项的域名部分，按方案顺序 |
| 4 | resolve：只在后面还有 IP 部分时才插入 |
| 5 | 各分流项的 IP 部分，按方案顺序 |
| 6 | 兜底 |

把所有分流项的域名部分排在所有 IP 部分之前，和 Clash 方案常见的 `no-resolve` 写法效果一致：命中域名的流量不会多做一次 DNS 解析。

指定了 DNS 服务器的规则，在它自己的路由规则之前还有一条 resolve，见 3.1。

### 2.1 局域网直连与用户认领的私有地址段

「局域网直连」仍然排在最前面（第 1 层），但**让出用户亲手写下的私有地址段**：

- **认领**：已启用并且**实际写进配置**的例外里的 IP 段，以及**实际写进配置**的分流项里**用户自己写的** IP 条目。
  - 订阅方案导入时带来的条目（例如机场模板里的 `IP-CIDR,192.168.0.0/16,DIRECT`）也是内联条目，但不算用户写的，不能认领。用户编辑这样的来源时，原来就有的私有段记为「继承的」，仍然不能认领；只有用户新加的段才算。来源上记一个「用户写的」标记，怎样保存、怎样给旧数据补上，见[数据与迁移](data-and-migration.md#3-分流状态格式-2用户写的标记)。
  - 还在等规则数据、或者因为资源上限没写进去的分流项，不会认领。
  - 只有完全落在局域网地址空间里的段才算（例如 `10.0.0.0/8`、`192.168.50.0/24`）；`0.0.0.0/0` 这类只是覆盖到的不算。局域网地址空间和内核的 `ip_is_private` 一致。
- **生成**：没有认领时，规则和以前一样是 `ip_is_private → 直连`。有认领时，改成逻辑规则「是私有地址，并且不在认领的段里 → 直连」。被认领的地址交给后面的规则，按原来的顺序匹配。
- **规则集不能认领**：方案和规则集里的内容永远不能把局域网流量拿走。
- **被认领的地址按正常顺序匹配**：和其他 IP 规则一样，所有分流项的域名部分排在 IP 部分前面。一个被认领的私有地址连接，如果嗅探出的域名命中了排在前面的某个分流项的域名规则，就按那个分流项走。所以这类分流项应该放在宽泛的方案分流项前面（在「我的方案」里可以调整顺序）。
- **测试网址**按同样的规则回答，见[用户体验](experience.md#6-测试网址)。

**为什么这样做。** 最初的设计是把局域网直连整个移到兜底之前，让"某个私有地址段 → 某个节点"这样的规则能生效。验证时发现这样会出问题：方案里的规则会抢走局域网流量。端到端测试里，`127.0.0.1` 命中了内置方案的「国内」IP 列表。实际使用中，一个经内部 DNS 解析到私有地址的域名，或者路由器管理页的域名，会被方案里宽泛的域名规则送去代理。所以改成现在这样，局域网直连留在最前面，只让用户自己写的规则优先。

## 3. DNS

- **只用域名部分生成 DNS 规则**。走向是"拦截"的直接拒绝；其余的分流项，用哪个 DNS 由它自身的固有属性（是不是国内）决定，不随当前走向变：国内分流项用国内 DNS，其余用远程 DNS。这样所有走向切换都是运行时切换。代价：国内分流项被改成走节点时，仍然向国内 DNS 解析。
- **例外**：走向是直连的用国内 DNS，其余用远程 DNS。
- **IP 部分不参与 DNS 规则**，避免 IP 类规则集在 DNS 阶段的匹配问题。
- **DNS 兜底**：兜底走向是"直连"时用国内 DNS，否则用远程 DNS。
- **设置了解析方式的规则**按 3.1、3.2 生成。
- **不会冲突**：DNS 规则和路由规则按同一个顺序生成。一个域名由哪条规则决定走向，就由同一条规则决定用哪个 DNS。例外排在所有分流项前面，所以例外的解析方式也排在前面。
- 其余与原有 DNS 设计一致。没有规则设置解析方式、也没有认领私有段时，生成的配置和第二轮设计（[概述](overview.md#12-第二轮内部网络与按环境切换)）之前完全相同。

**为什么不按走向选 DNS。** 最初的设计是按走向选 DNS（直连的用国内 DNS，其余用远程 DNS），但同时又要求在直连、地区自动、指定节点、跟随之间切换时不重启内核，两者互相矛盾：运行中的内核可以换出口，不能换 DNS 服务器。所以改成按分流项的固有属性选。

### 3.1 指定服务器（`dns=<服务器>`）

- 每个不同的「服务器 + 出口」组合生成一个 DNS 服务器。出口是分流项的选择器，所以在运行时切换走向，DNS 查询会跟着切换，不用重启内核。例外的出口是固定的；直连不设 `detour`，因为 sing-box 不允许 detour 到一个空的 direct 出站。
- 走代理时，UDP 查询要求节点支持 UDP；不支持的节点用 `tcp://`。
- 服务器写成域名时，用国内 DNS 解析它（国内 DNS 设成 `system` 时，在内网里就能解析内网的名字），不用公共的引导 DNS，以免把内网名字发给公共服务器。内网 DNS 最好直接写成 IP。
- `system` 不经过出口：系统 DNS 只能在本机查询。
- 以域名形式到达内核的连接（经本地 HTTP/SOCKS 代理端口）不会先查 DNS，直连出站会用国内 DNS 解析。所以在这条规则的路由规则之前，再加一条只对它的域名生效的 `resolve`，指定同一个服务器。以 IP 形式到达的连接（TUN）不受影响。排在例外之间那次 resolve 之后的规则不需要再加：那次 resolve 已经按 DNS 规则用这个服务器解析过。

### 3.2 由出口解析（`dns=exit`）

- 用 fake-ip 服务器（IPv4 `198.18.0.0/15`，开了 IPv6 时再加 `fc00::/18`）回答，并开启缓存文件的 `store_fakeip`，让内核重启后仍能认出旧的 fake-ip 地址。
- fake-ip 服务器**只在有规则用它时**才写进配置。它在配置里时，内核会把这个网段里的所有地址都当成 fake-ip，这个网段里真实存在的主机就连不上了。
- fake-ip 的回答 TTL 改写成 1 秒（内核默认是 10 分钟）。换环境、关掉最后一个「由出口解析」的分流项后，程序很快会重新查询并拿到真实地址，不会长时间拿着一个已经没有服务器能换回域名的 fake-ip。这些域名的 A/AAAA 查询返回 fake-ip，其他类型的查询返回空的 NOERROR，不能返回 NXDOMAIN，否则系统会认为这个名字不存在。
- 内核只对客户端发来的查询使用 fake-ip，自己的解析（resolve、直连出站解析域名）会跳过 fake-ip 规则，这正是需要的行为。
- 内核的 resolve 动作解析失败时会断开连接。所以例外之间插入的那次 resolve 要跳过这些域名，否则一条排在前面的 IP 类例外会让内网域名在 resolve 这一步就失败。跳过的条件和 DNS 规则的判断完全一致：在它后面的规则里，**第一条**匹配这个域名的规则是「由出口解析」，才跳过；如果更早的一条规则给这个域名指定了别的服务器，就照常解析。用逻辑规则写成：「在某个由出口解析的规则集里，并且不在它之前的任何其他规则集里」，取反。分流项 IP 部分之前的那次 resolve 不需要这个条件：能决定 DNS 的规则都在它前面，走到这里的域名一个都没匹配上。
- 走向是直连时，「由出口解析」就是由直连出站解析，用的是国内 DNS。
- 走向是拦截时，解析方式不起作用，这些域名的查询直接被拒绝。

## 4. agent 侧的调整

- **资源数量上限**：从 64 个提高到 256 个。单个文件 16 MiB、总计 64 MiB 的大小上限不变。
- **新的组类型**：在策略白名单里登记第 1 节的 `preferred`（"首选 + 备用"）组类型。
- 其他安全边界不变：只接受 `res:` 本地规则集，不接受远程规则集，agent 不联网。

## 5. 系统路由：验证结论，暂缓

原先设想加一个「系统路由」走向，让经其他组网工具或 VPN 的地址不进入 TUN、由系统路由表处理。按 sing-box 1.14.4 的源码验证：

- 开启 `auto_detect_interface` 时，出站连接绑定的网卡是**自身子网包含目标地址的那块网卡**（`interfaceFinder.ByAddr`），找不到时才用默认网卡。所以目标在组网工具自己的子网里，或者节点地址在这个子网里，用普通的直连就能走通，不需要系统路由。
- 只有**经路由而非同一子网**到达的地址（例如另一个 VPN 推送的一个大段路由，网卡地址不在这个段里）才会被错绑到默认网卡。

这种情况比原先设想的少，并且要改 TUN 路由，每次开关都要重建 TUN。所以先不做，等有具体场景再加。设计保留：作为一种走向，只接受 IP 段，写进 TUN 的 `route_exclude_address`。
